### P0-2 安装包没进云存储，发布索引表也没人读

- 现状：
  - `app_releases` 表（`version_name / version_code / apk_url / size_bytes / sha256 / published_at`）已建，但全仓库搜不到任何读取它的代码。
  - `apk_url` 目前指向仓库 `dist/` 的 raw 地址（`raw.githubusercontent.com/.../dist/MoreCheck-x.y.z.apk`）。因为 `dist/*.apk` 已入库，这个地址可下载（Range 请求 206 已验）；但它不是云存储，也不适合做灰度/统计。
  - 云存储上传没有可用的管理接口（当前 MCP 只有 list），所以 APK 字节没进桶。
- 影响：将来做"应用内下载安装包 / 版本分级"时没数据源；现在的检查更新只能甩给浏览器。
- 做法（建议顺序）：
  1. 先保持 `apk_url` 指 GitHub Release 资产（比 raw 更正式），发版时同步更新这张表；
  2. 若要字节入云：在已登录的设备上用应用内上传，或走云控制台手动上传到 `runtime` 桶，再把 URL 写回表；
  3. 客户端新增 `AppReleaseRepository`（读 `app_releases`，按 `version_code` 倒序）+ 在"关于 → 检查更新"里展示列表，正式版免登录可看（前提是该表配置为公开只读）。
- 注意：这张表如果是公开可读，**不要**写内部备注、测试账号、未发布版本信息。

### P0-3 1.1.70 没有云同步（只有登录态）

- 现状：1.1.70 已接入 `data/cloud` 的认证四件套（登录/注册/验证码/密码），但数据层没有 `SyncTombstone`、`PendingRecord`，`CheckDao` 也没有同步需要的方法，`CheckDatabase` 是 v2（1.1.90 是 v4）。登录成功后只拿到账号信息，打卡数据仍在本地。
- 影响：1.1.70 用户换设备后看不到旧数据；同一账号在两版之间切换会以为"数据丢了"。
- 做法（不是拷几个文件就完事）：
  1. 从 1.1.90 移植 `CloudDatabaseClient`、`CloudStorageClient`、`CloudSyncRepository`、`SyncStateStore`、`reminder/CloudSyncWorker`；
  2. 补 `SyncTombstone` / `PendingRecord` 实体与 DAO 方法，写 Room 迁移 2 → 4（**不要**用 `fallbackToDestructiveMigration`，会清用户数据）；
  3. 接 `ui/cloud/CloudSyncScreen` 与 `FirstLoginStrategyDialog`，`AppContainer` 挂仓库，`MoreCheckApp` 排 24h 周期任务；
  4. 真机双设备验证：A 打卡 → 同步 → B 拉取；B 删除 → 同步 → A 墓碑生效。
- 如果决定不做：在 README 与"我的 → 关于"里明确写"1.1.70 仅支持账号登录，不同步数据"，避免用户误解。

### P0-4 忘记密码没有入口

- 现状：登录页只有"验证码登录 / 密码登录"，没有"忘记密码"。云端支持 `PASSWORD_RESET` 验证码流程（上游 1.2.6 已实现，服务端契约见上游 `docs/history/08`），当前版本没接。老用户改密码需要旧密码做 sudo，也没有界面。
- 影响：忘记密码只能用验证码登录；想改密码无路可走。
- 做法：新增"忘记密码"页 → 发 `PASSWORD_RESET` 验证码 → 校验通过后设新密码（无需旧密码）。服务端行为先按上游契约表核对，再动 UI。
- 临时口径：README FAQ 已写"可改用验证码登录"，保持与实现一致。

### P0-5 签名密钥没有备份记录

- 现状：`keystore/morecheck.jks` 只在工作区，已被 `.gitignore` 排除；口令在 `keystore.properties`。没有任何离线备份。
- 影响：**密钥或口令丢失 = 无法给老用户发升级包**，只能换包名/换签名让用户卸载重装（本地数据全丢）。这是本项目最大的单点风险。
- 做法：立即离线备份 jks + 口令（加密压缩、至少两处），并在团队内指定保管人。备份成功后在本文打勾，不要记录口令本身。

## P1

### P1-1 应用内更新日志还是上游文案

- `ui/settings/ChangelogScreen.kt` 的 `RELEASES` 首条 `v1.1.90` 仍然只写"日历当天记录去掉收起按钮…"——那是上游 1.1.90 的改动，没有体现 MoreCheck 的裁剪（去天气/热搜/待办）、自有云、密码登录、新图标、新赞赏码。
- 用户点"更新日志"看到的与实际不符。建议重写 1.1.90 与 1.1.70 两条，例如：
  - 1.1.90：全新应用图标；支持手机号密码登录；打卡数据可同步到云端；移除天气、热搜与今日待办；修复若干细节问题。
  - 1.1.70：支持手机号密码登录；全新应用图标；移除天气；修复若干细节问题。
- 历史条目（1.1.2 ~ 1.1.82）保留上游原文即可，它们描述的是同源代码的真实历史。

### P1-2 两版可替换图标集合不同，别照搬

- 1.1.70：`default / blue / purple / orange / check / star / flame / leaf / tree / checklist / calendar`（11 套，alias、id、选择器、mipmap 四处一致）。
- 1.1.90：`default / check / star / flame / leaf / tree / pine / snow / mint / checklist / calendar`（11 套，同样四处一致；上游在此版删了蓝紫橙）。

### P1-3 `CloudConfig.kt` 注释还引用已删除的 `WeatherRepository`

- 1.1.70 / 1.1.90 的 `CloudConfig.kt` 顶部注释用 `WeatherRepository` 的 10 秒超时做对比，天气已删。纯注释问题，不影响编译，顺手改掉即可。

### P1-4 README 对 1.1.70 的能力边界写得不够直白

- 现在只在括号里写"1.1.70 目前仅提供账号登录"。但 1.1.70 与 1.1.90 的差距不止同步：实验室 4 项 vs 13 项、体积 6.45 MB vs 7.19 MB。
- 建议在版本表下加一句："1.1.70 不含实验室扩展功能（游戏、课程表、番茄时钟等），也不支持云同步；需要完整功能请用 1.1.90。"

### P1-5 云同步是行级 LWW，多设备并发会整行覆盖

- 机制：push 前逐行比对云端 `updated_at`，远端更新则跳过；pull 按各表水位线拉取；删除走墓碑。**没有字段级合并**。
- 后果：两台设备同时改同一个任务的不同字段，后同步的那台会整行覆盖前者。
- 这不算 bug（设计如此），但需要在同步页文案或 FAQ 里说清"建议一台设备为主"。若要做冲突提示，可在 pull 前比较本地/远端 `updated_at` 差值并弹窗。

### P1-6 图标切换后桌面刷新有延迟（系统行为）

- 切换 `activity-alias` 后部分启动器要几秒到几十秒才换图标，个别机型要等下次桌面重绘。不是代码 bug，别为此加"强制刷新"的 hack。

### P1-7 1.1.50 重建包与上游原版不等价

- 上游 `v1.1.50` tag 里的源码实际是 1.1.42 beta。原版 `original-apks/CheckInMate-1.1.50.apk` 里有「主题色」设置，重建包没有（字符串比对可复现）。
- 影响：把 1.1.50 当作"1.1.50 官方功能"来宣传会名不副实；它更像 1.1.42 + 主题模式。
- 处理：这版只作历史归档，README/版本历史已标注；若要补齐，只能从原版 APK 逆向或找到真正的 1.1.50 源码，不建议投入。新功能一律做在 1.1.90。

## P2

### P2-1 上游参考快照差点被提交（已处理）

- `sources/v1.2.0`、`sources/v1.4.0` 是上游 CheckInMate 的原样快照，各自带 `.git` 和 `CheckInMate/keystore/checkinmate.jks`。它们曾是未跟踪状态，`git add -A` 会把整个私有仓库作为 embedded repo 提交进公开仓库。
- 已在 `.gitignore` 加 `/sources/v1.2.0/`、`/sources/v1.4.0/`。**不要再取消这两条**；要基于上游出新版，按 HANDOVER 7.1 导出干净目录。
- 定期检查：`git status --short` 不应出现这两个目录。

### P2-2 `rebrand.py` 的域名替换是个坑

- 脚本会把 `checkinmate-sync.app.workbuddy.host` 一起替换成不存在的 `morecheck-sync.app.workbuddy.host`，曾导致 1.1.90 云登录整条链失效（发现时已经发过包）。
- 脚本本身在 `.gitignore` 里（不入公开仓库），接手者需要从上一任拿副本。
- 建议改法：脚本只替换品牌词与包名，**域名单独列白名单**（或替换后立刻断言 `CloudConfig.ENDPOINT == "https://morecheck.app.workbuddy.host"`，不匹配就退出）。

### P2-3 没有 CI，也没有自动化发版

- 构建、校验、改 README 哈希、建 Release 全靠手动，容易漏。至少可以加一个 `scripts/release.sh`：构建 → 三查 → 复制 dist → 打印新哈希 → 提示要改的文件。是否接 GitHub Actions 取决于是否愿意把签名密钥放进 Secrets。

### P2-4 `dist/*.apk` 入库，仓库会持续变大

- 四个包约 20 MB，且每次发版都会新增二进制差异（Git 对 APK 的 delta 效果很差），仓库会持续变大。目前靠它给 `raw.githubusercontent` 提供下载。
- 若改用 Release 资产作为唯一分发渠道，可把 `dist/` 加入 `.gitignore`；但要注意 `app_releases.apk_url` 与 README 下载链接都要跟着改。

### P2-5 构建依赖在线解析

- 首次构建需要联网拉依赖；换机器时先联网构建一次，之后可 `--offline`。`1.1.70` 历史上就出现过 4 个依赖未缓存导致构建失败。

### P2-6 版本号与 tag 规范尚未落地

- 现在只有约定（沿用上游、`versionCode` 只增），没有强制校验，也没有 tag。建议在 HANDOVER 7.2 的清单里固定"先打 tag 再发 Release"，并在发版脚本里校验 `versionCode` 大于上一版。

### P2-7 单元测试很少

- 1.1.90 只有 4 个测试文件（云模型、课程表解析、知识检索、连续打卡）。核心的同步合并、墓碑、首次登录策略都没有测试。
- 改动 `CloudSyncRepository` 或 Room 迁移时，至少补纯 JVM 测试（不需要模拟器）。

## 接手前必读的注意事项

1. **签名、包名、云环境三者绑定一个产品身份**，任何一个都别改。改之前先想清楚老用户怎么升级。
2. **发版必须 `assembleRelease`**，并且真机走一遍：启动 → 打卡 → 统计 → 我的 → 关于 → 检查更新。
3. **改功能就改隐私政策**：删功能要删条款、删权限；加联网要加说明。隐私政策日期与版本号在 `PlaceholderScreen.kt`。
4. **云端单会话**：调试时别反复登录，会把用户手机踢下线。
5. **构建不可复现**：同源码两次构建哈希不同，校验只认文件哈希。
6. **1.1.70 与 1.1.90 是两条并行线**，不要为了"代码统一"把 1.1.90 的功能整包倒灌进 1.1.70——那等于重做一次发布，且会带来 Room 迁移风险。
7. 上游（CheckInMate 1.4.0）的已知问题清单**不直接适用**于本裁剪版：音乐、B 站、热搜等模块这里没有，别照着上游文档去"修"。
